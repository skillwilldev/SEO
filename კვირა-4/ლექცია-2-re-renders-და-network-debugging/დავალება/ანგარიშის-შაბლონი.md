## 2. პრობლემა #1 — შეცდომიანი request „წარმატებად" ჩანს

| ღილაკი | URL | Status (Network) | რა ჩანს გვერდზე | ჩანაწერი |
|---|---|---|---|---|
| ტიკეტების ჩატვირთვა | tickets.json | 200 OK | ტიკეტები ჩატვირთულია | წარმატება |
| არქივის ჩატვირთვა | /tickets-archive.json | 404 Not Found | შეცდომა არ ჩანს / ცარიელია | შეცდომა 404 |

**რა დააბრუნა 404-მა Response tab-ში:** - HTML შეცდომის გვერდი / ტექსტი "Not Found"

**რომელი შემოწმება აკლია `api.js`-ს:** - if (!response.ok)

**რატომ არ ჩნდება შეცდომა ინტერფეისზე (`ApiPanel.jsx`):** - fetch არ აგდებს ექსოპშენს HTTP შეცდომებზე (4xx/5xx) და კოდი ცდილობდა მიღებული HTML პასუხის JSON-ად პარსვას

**რატომ არ აგდებს `fetch()` შეცდომას 404-ზე (და როდის აგდებს):** - fetch() პრომისს აბრუნებს უარყოფითად (reject) მხოლოდ მაშინ, როდესაც ფიზიკურად ქსელური შეცდომაა (ინტერნეტი არ არის, DNS ვერ პოულობს და ა.შ.). 404 ან 500 სტატუსის დროს კი სერვერი პასუხობს, ამიტომ fetch() პრომისი წარმატებულია (ok: false დროშით)

**`JSON.parse`-ის „ჩაყლაპული" შეცდომა — რა იქნებოდა მართებული:** - პარსვამდე სტატუს-კოდის შემოწმება და ექსპლიციტური შეცდომის გამოტანა (throw new Error)

**გამოსწორება:**

```js
// before
const res = await fetch(url);
return await res.json();

// after
const res = await fetch(url);
if (!res.ok) throw new Error(`HTTP error! status: ${res.status}`);
return await res.json();
```

## 3. პრობლემა #2 — request-ების ნაკადი

| | მნიშვნელობა |
|---|---|
| „გაგზავნილი request-ები" 3 წამში | 100+ |
| Network tab-ში ჩანაწერების რაოდენობა | ასობით |
| ერთი და იგივე URL იმეორება? | კი |

**რომელი state იცვლება ყოველ ციკლზე:** - searchTerm / ძიების შედეგების სტეიტი

**არასტაბილური dependency და რატომ:** - არამემოიზებული ფუნქცია ან ობიექტი, რომელიც ყოველი რენდერისას თავიდან იქმნება და იწვევს useEffect-ის ხელახლა გაშვებას

**ციკლი 4 ნაბიჯად:** `render → useEffect → setState → render`

**რატომ არ შველის `[]` dependency მასივი:** - თუ ეფექტის შიგნით გამოყენებული ფუნქცია ან ცვლადი ეყრდნობა გარე სკოპს, ცარიელი მასივიც კი ვერ იცავს არასტაბილური ქცევისგან, ან იწვევს დაკავშირებული სტეიტების უსასრულო განახლებას

**გამოსწორება (+ debounce):**

```js
// before
useEffect(() => { fetchResults(query); }, [query, fetchResults]);

// after
useEffect(() => {
  const timer = setTimeout(() => { fetchResults(query); }, 300);
  return () => clearTimeout(timer);
}, [query]);
```

**შემოწმება:** `ნინო`-ს აკრეფაზე გაიგზავნა 1 request

**გვერდზე ნაჩვენები ჯამური დრო:** ~90 ms | **ცალკეული:** 30 + 30 + 30 ms

**waterfall-ის ფორმა (before):** - კიბისებრი (თანმიმდევრული)

**მიზეზი (`api.js` → `loadDashboard`):** - მიმდევრობითი await fetch(...) გამოძახებები ერთმანეთის მიყოლებით

// before
const tickets = await fetchTickets();

## 11. დასკვნები

1. **რომელი პრობლემა ვერ იპოვებოდა Network tab-ის გარეშე და რატომ?** - მოთხოვნების უსასრულო დუბლირება (ციკლები), 404 შეცდომების არასწორი ინტერპრეტაცია და waterfall მოთხოვნები, რადგან ინტერფეისში ეს აისახება მხოლოდ შენელებად ან ცარიელ ეკრანად, ხოლო რეალური ქსელური მიზეზი ჩანს მხოლოდ Network tab-ში

2. **რომელი პრობლემა ვერ იპოვებოდა Profiler-ის გარეშე და რატომ?** - SlaPanel-ის მძიმე გამოთვლები და კომპონენტების ზედმეტი რენდერები, რადგან Profiler ზომავს შესრულების მილიწამებს და ზუსტად მიუთითებს კომპონენტის განახლების მიზეზს (Why did this render?)

3. **`React.memo`, `useMemo`, `useCallback` — რომელი როდის გამოიყენება? (3 წინადადება)** - React.memo ამემოიზებს კომპონენტებს და არ აძლევს მათ უსარგებლო რენდერის საშუალებას უცვლელი პროპებისას. useMemo ინახავს მძიმე გამოთვლების შედეგებს და ობიექტების მისამართებს ქეშში. useCallback ამემოიზებს ფუნქციებს და გამორიცხავს მათი ახალი მისამართით შექმნას ყოველი რენდერისას

4. **რატომ არის საშიში ამ სამი ინსტრუმენტის „ყველგან" გამოყენება?** - ზედმეტი ხარჯების გამო: React ხარჯავს დამატებით მეხსიერებას და პროცესორის რესურსს ქეშირებასა და მუდმივ შედარებებზე, რამაც შეიძლება მარტივი კომპონენტების მუშაობა უფრო გაანელოს

5. **რა უნდა შემოწმდეს ყოველი `fetch()`-ის შემდეგ, სანამ მონაცემებს გამოიყენებ?** - აუცილებლად უნდა შემოწმდეს response.ok დროშიში, რადგან fetch სერვერის 4xx/5xx პასუხებს ქსელურ შეცდომად არ თვლის და აბრუნებს წარმატებულ პრომისს
