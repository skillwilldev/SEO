## 2. ბაგი #1 — ქვეჯამი

**Scope-ის დაკვირვება:**

| iteration | `i` | `items.length` | `subtotal` |
|---|---|---|---|
| 1 | 1 | 1 | 0 |
| 2 | - | - | - |

**მიზეზი:** ციკლი იწყებოდა `let i = 1`-ით, ამიტომ ერთადერთი ელემენტი (`items[0]`) სრულად გამოტოვებული იქნა ჯამის დათვლისას.

**გამოსწორება:**

```js
// before
for (let i = 1; i < items.length; i++) {
  subtotal += items[i].price * items[i].quantity;
}

// after
for (let i = 0; i < items.length; i++) {
  subtotal += items[i].price * items[i].quantity;
}
```

## 4. ბაგი #3 — წაშლა

**Logpoint-ის გამონატანი:** `dishId = 2`

**Call Stack (ზემოდან 3):** `handleRemoveDish -> dispatchSetState -> scheduleUpdateOnFiber`

**მიზეზი:** App.jsx-ში filter აბრუნებდა ახალ მასივს, მაგრამ მდგომარეობა არ იცვლებოდა, რადგან setOrder არ გამოიძახებოდა. ასევე BillItem.jsx-ში item.dishId იძებნებოდა, როცა ობიექტს ერქვა item.id

**რატომ არ ჩანს Console-ში შეცდომა:** იმიტომ რომ filter მეთოდი ლეგიტიმურია და არარსებული პროცესების გამოძახება (როგორიცაა undefined-ის გადაცემა ფუნქციაში) უბრალოდ აბრუნებს undefined-ს და არ აგდებს ქრაშს

**გამოსწორება:**

```jsx
// before
const handleRemoveDish = (dishId) => {
  prevOrder.filter(item => item.id !== dishId);
};

// after
const handleRemoveDish = (dishId) => {
  setOrder(prevOrder => prevOrder.filter(item => item.id !== dishId));
};
```

## 5. ბაგი #4 — ცარიელი ანგარიშის დახურვა

**Debugger შეჩერდა:** ფაილი `src/components/Checkout.jsx` ხაზი `20`

**შეცდომის ტექსტი:** TypeError: Cannot read properties of undefined (reading 'name')

**რატომ არის `order[0]` -> `undefined`:** order[0] -> undefined: რადგან კალათა ცარიელია (order = []), მასივში არცერთი ელემენტი არ ფიქსირდება და მითითებული ინდექსი ([0]) აბრუნებს undefined-ს

**რატომ რჩება ღილაკი „დამუშავება..." რეჟიმში:** შეცდომის გამო კოდის შესრულება შეწყდა (uncaught exception) და setIsProcessing(false) ბლოკამდე ვერ მივიდა

**გამოსწორება:**

```jsx

const handleCloseBill = async () => {
  setIsProcessing(true);

};

// after
const handleCloseBill = async () => {

    return;
  }
  setIsProcessing(true);
  try {
    const firstDishName = order[0].name;
    // ...
  } finally {
    setIsProcessing(false);
  }
};
```

## 6. ბაგი #5 — მომსახურების საფასური

**Conditional breakpoint-ის პირობა:** amount > 50

**Watch expressions:**

| გამოსახულება | მნიშვნელობა |
|---|---|
| `subtotal * (servicePercent / 100)` | 6.75 |
| `fee` | 6.75 |
| `roundedFee` | 6 (მანამდე), 6.75 (ახლა) |

**მიზეზი (`parseInt` vs `Math.round`):** (parseInt vs Math.round): parseInt მთლიანად ჭრის წილად ნაწილს და ტოვებს მხოლოდ მთელ რიცხვს (6), ხოლო Math.round აკეთებს მათემატიკურ დამრგვალებას. კოპეკების/თეთრების შესანარჩუნებლად საჭიროა გამრავლება და გაყოფა 100-ზე

**რატომ ჯობია conditional breakpoint ჩვეულებრივს:** რადგან აპლიკაციის რენდერისას ან სავაჭრო კალათის განახლებისას ეს ფუნქცია შეიძლება ასჯერ გამოიძახოს, ხოლო conditional breakpoint აჩერებს დევაგერს მხოლოდ მაშინ, როცა ჩვენთვის საინტერესო პირობა დაკმაყოფილდება

**გამოსწორება:**

```js
// before
const roundedFee = parseInt(fee);

// after
const roundedFee = Math.round(fee * 100) / 100;
```

## 9. დასკვნები

1. **რომელი breakpoint-ის ტიპი აღმოჩნდა ყველაზე სასარგებლო და რატომ?** ყველაზე უნივერსალური აღმოჩნდა Line-of-Code Breakpoint Scope პანელთან ერთად, რადგან ის საშუალებას გვაძლევს ხაზ-ხაზ ვნახოთ ცვლადების ცვლილებები. ხოლო Exception Breakpoint გადამწყვეტი იყო მე-4 ბაგის სწრაფად საპოვნელად
